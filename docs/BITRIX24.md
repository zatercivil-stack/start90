# Битрикс24: проект интеграции, не подключение

В MVP нет API-вызовов, credentials или имитации соединения. Не было доступа к порталу ТГТ. Ни автор, ни этот проект не заявляют опыта внедрения в ТГТ.

Проверены официальные источники:
- [Событие OnTaskAdd](https://apidocs.bitrix24.ru/api-reference/tasks/events-tasks/on-task-add.html)
- [Создание tasks.task.add](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-add.html)

OnTaskAdd сообщает о созданной задаче. Это не готовое событие «сотрудник принят». Сначала нужно выяснить, каким шаблоном или полями компания обозначает приём, кто назначает наставника, откуда берётся дата выхода и как соотносятся ID сотрудников.

## Предлагаемая граница адаптера

Вход: `EmployeeStarted { portalId, sourceTaskId, employeeExternalId, displayName, department, position, startDate, managerExternalId, mentorExternalId? }`.
Выход: `HelpRequested { issueId, employeeExternalId, title, description, responsibleExternalId, dueDate }`.

Это описание будущего контракта, а не реализованный API. Сначала серверный адаптер сопоставляет поля и проверяет права; доменная логика не должна знать webhook URL или формат конкретного портала.

## Пилотный поток

1. Подписаться на согласованное событие, проверить подлинность и портал, получить задачу.
2. Отфильтровать задачи приёма по согласованному признаку; не разбирать названия задач догадками LLM.
3. Создать адаптацию идемпотентно: уникальная пара `(portalId, sourceTaskId)` предотвращает повторное создание.
4. При согласованном запросе помощи вызвать `tasks.task.add` с TITLE, RESPONSIBLE_ID, DEADLINE и обязательными пользовательскими полями конкретного портала.
5. Сохранить соответствие локального issueId и ID задачи. Доставлять через outbox с повторными попытками и журналом; не создавать дубли при повторе.
6. В первой версии не делать двустороннюю синхронизацию статусов. Завершение задачи руководителем не должно автоматически подтверждать решение от имени новичка.

До реализации проверить доступность REST на тарифе, права сервисной учётной записи, пользовательские поля, назначение ответственных, лимиты, повторную доставку и требования к хранению персональных данных. Все секреты — только на сервере. Для обращений к HR отдельно ограничить видимость и исключить отправку руководителю по умолчанию.
